---
name: orch-dispatch
description: Start, steer, check and clean up worker sessions. Use for /orch run <task>, when the user asks for work with Codex or with both models, when a worker reports done or blocked, to relay an answer into a session, or to close finished work.
---

All commands run in orch's directory as `npm run -s orch -- <command>`; rules are in `policies.md` under Relay and steering, Workers, and Claude, Codex and pairs.

run: `run <repo> <name> [task] [--kind claude|codex|both] [--from <ref>]`. Claude workers start in poteto-mode automatically; their full brief is written to `briefs/<name>.md`. `<repo>` is a registered name, a path, or a folder under the code dir (`ORCH_CODE_DIR`, default ~/code). Kind: what the user said ("with Codex" is codex, "both" or "duel" is both), else the plan task's tag, else claude; tag `(both)` yourself for the risky task types in `policies.md`. Without a task, the text comes from the `<name>` task in `plans/<repo>.md`. Both starts `<name>-cl` and `<name>-cx`. Tell the user names and panes in one line. If it says not ready, read the pane and file a decision.

done: a `DONE worker <name>` line from the watcher. For a pair worker, wait until both are done, then `judge <pair>`: report the winner and why, mark the plan task `[x]`, ship the winner as below, and file a decision for abandoning the loser. For a single worker, run `gates <name> -m "<what this round did>"`; on a pass it makes the worker's commit. Pass: mark the plan task `[x]`, one FYI line, then ship. Fail: `steer <name>` once with the failing tail; a second fail is a decision.

ship (Autonomy in `policies.md`): `review <repo> <branch>` and verify single-model findings. A surviving blocking finding: steer the worker once to fix it, then gates and review again; still blocking is a decision. Clean: `push <name>`, then `open-pr <name>` for a new branch (a `pr<n>` worker updates its PR by the push). Then `merge <repo> <n>`; if checks are pending, retry on the next planning pass or brief. Any command refusing because its switch is off: file a decision and rerun with `--accepted D-NN` after the accept. Never ship work that touches deploys or databases; that stays a decision.

overlap: `overlap [<repo>]` lists every pair of running workers on a repo whose branches would change the same files if merged now (committed or not, conflicts included), or says `no overlap`. A Claude/Codex pair doesn't count, nor a worker `run --from` the branch head of a worker with commits of its own and that parent (recorded as `parent` in workers.json), nor a worker whose head a merged PR already had (new commits on a reused branch count again). A repo whose fetch fails is skipped with `OVERLAP error: <repo>: git fetch origin failed ...; skipped`; the others are still checked. A failed `gh pr list` prints `OVERLAP error: <repo>: gh pr list for <worker> failed: ...` and the worker is still checked. An unknown origin/HEAD is learned once with `git remote set-head origin -a`, else origin/main is used with an `OVERLAP warning:` line. The watcher runs it every 10 minutes (one run at a time, killed after 5 minutes; a failure prints `OVERLAP error: ...`, which orch fixes like a `BRIDGE error`) and prints `OVERLAP <repo>: <later> (later) and <earlier> both change N files: ...` once per pair, again only when files join. On that line, `steer <later> "<earlier> changes <files> too: merge origin/<default> into your branch now and keep your change out of its way; say so in your report"` (SendMessage if it is a peer). If both rework the same function, file a decision on which one goes first. FYI to the user, no push.

behind its base: `merge <repo> <n>` refuses a PR that is behind its base branch (`not merged: #N is K commits behind main. Have <name> merge origin/main into its branch ...`) and merges only the head it checked (`--match-head-commit`). Steer the worker to merge origin/<base> into its branch (a merge commit, never a rebase) and rerun its gates, then `gates`, `push` (a normal push, history is not rewritten) and `merge` again; a branch that contains the base's head is not behind. A base commit whose change the PR already holds (its parent's squash merge) doesn't count, so a stacked child merges after its parent without updating; retarget it to the default branch first (`gh pr edit <n> --base main`); merge refuses while it targets an `orch/` branch whose head a merged PR had, and stops with `merge stopped: gh pr list ... failed` when it cannot tell. Nobody rebases or force-pushes a pushed branch. A colleague's PR behind its base: ask its author to update it.

blocked or question from a worker: same as any session, a decision. Answer only with the user's words.

steer: `steer <name|pane> "<text>"`. For a new substantial task in one of the user's sessions, start the text with `/pstack:poteto-mode ` and keep it on one line (a newline turns it into pasted text and the slash command never runs). Relaying an answer or follow-up to a Claude session: SendMessage first when it is a ListAgents peer (match by session id in `sessions.json`); it lands in the session's queue without touching the input box, so it works while the user has the pane open. Type with `steer` only for Codex, for non-peers, and for slash commands like poteto-mode (SendMessage can't run those). `steer` refuses only when the user is actually typing in the pane (text in the input box, suggestions ignored) or the pane is blocked on a dialog; then use SendMessage, or give the user the text.

cleanup: `cleanup <name>` once the work is merged or abandoned. A refusal lists the unsaved work; file a decision, and only after the user agrees run `cleanup <name> --abandon`. The branch is always kept.

workers: `workers` lists running workers with live status and the cap.
